# 広告表示最後処理と重複防止計画

## 概要

広告表示ペアを順番制御対象の最後に回し、直前処理が成功した後に約3分待ってから処理する。

あわせて、1分トリガーの重なりと同一ファイルIDの同時処理を防ぐ。

## 実装方針

- `processInputFolder()` 全体に `LockService.getScriptLock().tryLock()` を入れる。
- ロック取得できない実行は、何も処理せず終了する。
- ロック取得できた実行だけが処理を進め、最後に必ず `releaseLock()` する。
- `PropertiesService` でfileId単位の処理中ガードを管理する。
  - 処理開始前に `processing` を記録する。
  - 処理終了時に `processing` を削除する。
  - 既に `processing` のfileIdは、その回では処理しない。
  - 成功済みfileIdの長期記録は残さない。
- 順番制御の処理順を以下に変更する。
  1. RPPトラック
  2. 楽天サーチ
  3. 3分待機
  4. 広告表示ペア
- 広告表示ペアの3分待機は `Utilities.sleep` を使わず、`PropertiesService` に待機開始時刻を保存して判定する。
- 3分未満なら広告表示ペアを `input` に残して終了する。
- 3分以上経過したら広告表示ペアを処理し、成功・失敗にかかわらず待機状態をクリアする。
- 既存の広告表示ペア単位ガード `RPP_UNYOU_PAIR_...` は残す。
- `README.md` に、広告表示ペアが順番制御対象の最後で3分待機後に処理されることと、重複防止の概要を追記する。

## エラー時の扱い

- RPPトラックまたは楽天サーチでエラーが出た場合は、現行どおり後続処理を実行しない。
- 前段エラー時は、未処理の広告表示ペアも現行ルールどおり `error` へ移動する。
- 広告表示ペアの片方不足や同種重複は、現行どおりエラー扱いにする。
- 待機中に広告表示ペアが `input` から消えた場合は、待機状態をクリアする。
- 処理失敗時もfileIdの `processing` は必ず削除し、処理中状態を残さない。

## テスト観点

- 1分トリガーが重なっても、同時に2つの `processInputFolder()` が処理を進めない。
- 同じfileIdが処理中の場合、二重に子GASへ送信されない。
- RPPトラック、楽天サーチ、広告表示ペアを同時に置いた場合、広告表示ペアが最後に処理される。
- 楽天サーチ成功後、広告表示ペアは3分未満では処理されない。
- 3分以上経過後、広告表示ペアが処理される。
- 広告表示ペアだけを置いた場合も、検知後に3分待ってから処理される。
- 処理失敗後に `processing` 状態が残らない。

## 前提

- 「一番最後」は順番制御対象内の最後とする。
- 通常ファイルは従来どおり、順番制御対象の処理完了後に処理する。
- 成功済みfileIdの長期保存はしない。
- トリガー間隔は1分のまま変更しない。
- 子GAS側の処理内容とURLは変更しない。
