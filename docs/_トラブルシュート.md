# RPP item_list トラブルシュート

作成日: 2026-04-10

## 概要

`01input` に `YYYYMMDD_item_list.csv` を配置したとき、親GASの `log` シートに子GASエラーが記録され、`RPP-Track` への取込が失敗する事象が発生した。

今回の対応で、`item_list.csv` は以下の仕様で動作する状態に修正済み。

- 親GASは `YYYYMMDD_item_list.csv` を `RPP-Track` へ振り分ける
- 子GASは ZIP 固定ではなく、`ZIP / CSV` の両方を受け付ける
- `item_list.csv` は `B3` の表示期間日付を取り込み日付として扱う
- 取込先 `商品売上` シートの `A列=日付` に日付を入れる
- 同じ日付のデータが既に存在する場合は、上書きせずエラーにする

---

## 今回の実原因

今回の事象は、単一原因ではなく複数要因が重なっていた。

1. `RPP-Track` の実行中 web app が、`item_list.csv` を想定した最新ローカルコードと一致していなかった
2. 子GAS側に ZIP 前提の処理や旧デバッグ応答が残っており、`item_list.csv` が正常経路に入らない状態があった
3. `item_list.csv` は ZIP ではなく CSV なので、`application/zip` 前提の判定では失敗する
4. `item_list.csv` の取込先シートの実ヘッダーが、実装側の想定と一致していなかった
   - 実シート: `日付`
   - 実装側の途中想定: `対象日`
5. 同日データの再投入時に、重複をどう扱うかの仕様が未確定だった

---

## 原因として考えられるもの一覧

次回同様の不具合が起きたときは、以下を原因候補として上から順に確認する。

### 1. 親GASの振り分け条件ミス

- `CHILD_SCRIPTS` に `YYYYMMDD_item_list.csv` の正規表現が入っていない
- `rpp_` 側のエントリが bridge や旧URLのままになっている
- 親GASの `clasp push` が漏れている

### 2. 親GASの呼び出し先URLが古い

- ローカルでは修正済みでも、親GASが旧 web app URL を呼んでいる
- bridge 用 URL の戻し忘れがある
- 子GASを新規デプロイしたのに、親GAS側のURL差し替えが未実施

### 3. 子GASのデプロイ不整合

- ローカルコードは修正済みだが `clasp push` していない
- `clasp push` 済みでも、web app を新バージョンで再デプロイしていない
- `/exec` で動いているコードとローカルファイルの内容が一致していない

### 4. 子GASが ZIP 固定で判定している

- `.zip` や `application/zip` 前提でしか分岐していない
- `item_list.csv` を CSV として扱う分岐がない
- ファイル名による救済判定がない

### 5. CSVの中身判定が厳しすぎる

- BOM付きUTF-8をうまく判定できない
- `商品分析` などの見出し検出が厳しすぎて落ちる
- ヘッダー開始行が想定と違う

### 6. 取込先シートのヘッダー不一致

- `商品売上` シートのヘッダー名が実装想定と違う
- `日付` / `対象日` の呼び方差異がある
- `商品管理番号` や `在庫数` など必須列名が実シートとズレている

### 7. 重複データの扱い未定義

- 同じ日付のデータが既にあるのに、削除・上書き・停止のどれで扱うか未定義
- 現在は `item_list.csv` のみ「同日データがあればエラー停止」

### 8. バインド先スプレッドシートの問題

- `RPP-Track` は `SpreadsheetApp.getActiveSpreadsheet()` 前提
- web app の実行先が正しいバインドプロジェクトでないと、対象シートを取得できない

## エラー時に確認すること

### 1. 親GASログでまず見ること

- `child`
- `url`
- `HTTP status`
- `response body`

見るべきポイント:

- `child=RPPパフォーマンス取込 (RPP-Track)` になっているか
- `url` が最新の `RPP-Track` web app URL か
- HTTP 200 でも `response body` がエラー内容を返していないか

### 2. ファイル名と形式を確認する

- ファイル名が `YYYYMMDD_item_list.csv` になっているか
- 拡張子が `.csv` か
- 想定外のファイル名になっていないか

### 3. 子GASへ直接POSTして切り分ける

親GASを通さず、子GAS `/exec` へ直接 `fileId` を投げて確認する。

これで失敗する場合:

- 原因は親GASではなく子GAS側

これで成功する場合:

- 親GASのURL設定またはルーティング条件を疑う

### 4. 子GASのローカルと本番を確認する

- `clasp push` 済みか
- `clasp version` 済みか
- `clasp deploy` で新バージョンが web app に反映されているか
- 親GASがその新URLを使っているか

### 5. `商品売上` シートのヘッダーを確認する

現時点で前提としているヘッダー:

```text
日付
ジャンル
カタログID
商品ID
商品名
商品管理番号
商品番号
売上
売上件数
売上個数
アクセス人数
ユニークユーザー数
転換率
客単価
総購入件数
新規購入件数
リピート購入件数
未購入アクセス人数
レビュー投稿数
レビュー総合評価（点）
総レビュー数
滞在時間（秒）
直帰数
離脱数
離脱率
お気に入り登録ユーザ数
お気に入り総ユーザ数
在庫数
```

ズレていたら:

- 列名に合わせて `fieldMappings` または `requiredHeaderGroups` を修正する

### 6. `item_list.csv` の構造を確認する

現時点の前提:

- 1行目: 注意書き
- 2行目: `商品分析`
- 3行目: `表示期間`
- 6行目: ヘッダー
- 7行目以降: データ
- A列: `#` の連番
- 実データは B列以降ではなく、CSV上は `#` 列を含む1列目から解析してよい

重要:

- 取込日付は `B3` の日付ではなく、CSVの `表示期間` 行から取得している
- 取込先シートへは `A列=日付` として入れる

### 7. 重複有無を確認する

現在の `item_list.csv` の仕様:

- 既に同じ日付の行が `商品売上` に存在する場合はエラー停止

出るエラー例:

```text
同じ日付のデータが既に存在します: 2026-04-09
```

これは不具合ではなく、重複防止の仕様どおり。

## よくあるエラーと見る場所

### `Invalid argument: ContentType. Should be of type: application/zip`

確認箇所:

- 子GASが ZIP 固定判定のままではないか
- 旧デプロイURLを踏んでいないか
- `item_list.csv` を CSV 分岐へ入れているか

### `CSV のレポート種別を特定できませんでした`

確認箇所:

- BOM付きUTF-8の扱い
- `商品分析` 見出し判定
- `item_list.csv` をファイル名で救済判定しているか

### `商品売上 取込先シートの必須ヘッダーが不足しています`

確認箇所:

- `商品売上` シートの1行目ヘッダー
- `日付` / `対象日` の違い
- `商品管理番号` 列が存在するか

### `同じ日付のデータが既に存在します`

確認箇所:

- 同日データがすでに入っていないか
- 今回は再投入なのか初回投入なのか
- 上書きしたい運用に変える必要がないか

---

## 次回の標準確認手順

1. 親GAS `log` の `child / url / HTTP status / response body` を確認する
2. 親GASの `CHILD_SCRIPTS` のURLが最新か確認する
3. 子GASへ `fileId` を直接POSTして、親側か子側かを切り分ける
4. 子GASの `clasp push` と web app デプロイ版数を確認する
5. `商品売上` シートのヘッダー1行目を確認する
6. 対象CSVの `表示期間` と既存データ日付の重複を確認する
7. 仕様どおりならそのまま、仕様と違うなら重複処理ルールを見直す

---

## 運用メモ

- 子GASを修正しただけでは本番反映されない
- `clasp push` の後に web app の新規バージョンデプロイが必要
- さらに親GAS側の `webAppUrl` 差し替えと `clasp push` が必要
- `item_list.csv` は ZIP ではないため、今後も「ZIP 固定にしない」方針を維持する
