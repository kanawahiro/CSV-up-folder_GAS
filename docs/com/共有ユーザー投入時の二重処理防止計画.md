# 共有ユーザー投入時の二重処理防止計画

作成日: 2026-04-13

## 概要

共有ユーザーが `01input` にファイルを追加した場合にだけ処理が不安定になる主因は、親GAS `processInputFolder()` に全体ロックとファイル単位の処理済み管理がないことと考える。

特に `clickpostReport` では、加工済みCSVを `04output` に作成してから元ファイルを `02processed` へ移動するまでの間に、1分トリガーの次回実行が同じファイルを再検知すると、同じ出力処理が繰り返される可能性がある。

## 現状の問題

- `processInputFolder()` は `inputFolder.getFiles()` で見つけたファイルをそのまま処理している。
- 親GAS全体の同時実行を止める `LockService` が入っていない。
- 同じ `fileId` が処理中または処理済みかを判定する仕組みがない。
- `clickpostReport` は出力ファイル名に秒単位のタイムスタンプを付けるため、再処理されるたびに別名CSVが作成される。
- 共有ユーザーがアップロードしたファイルでは、Drive上の所有者・権限・同期反映の差により、処理タイミングのずれが出やすく、既存の再入問題が表面化している可能性が高い。

## 対応方針

今回は親GAS中心で対策する。

- 子GASの取込ロジックやWebアプリURLは変更しない。
- 親GAS側で同時実行と同一ファイルの二重処理を防ぐ。
- `clickpostReport`、通常の子GAS振り分け、RPP運用ペア処理のすべてに同じ再入防止方針を適用する。
- 処理結果とDrive上の移動結果が一致するようにする。

## 実装案

### 1. スクリプト全体ロックを追加する

`processInputFolder()` の冒頭で `LockService.getScriptLock()` を取得する。

- ロック取得できた実行だけが処理を継続する。
- ロック取得できない実行は処理せず終了する。
- 1分トリガーが重なっても、同時に複数の親GASが同じファイルを処理しないようにする。

### 2. `fileId` 単位の処理状態を管理する

`PropertiesService` を使い、ファイルごとの状態を記録する。

- `processing`: 処理中
- `done`: 処理済み

処理開始前に `processing` を記録し、成功またはエラー移動完了後に `done` を記録する。

既に `processing` または `done` の `fileId` はスキップする。

### 3. inputフォルダ残存確認を追加する

各ファイル処理前に、そのファイルがまだ `01input` に存在するか確認する。

- 既に `02processed` や `03error` へ移動済みなら処理しない。
- 他の実行によって移動されたファイルを再処理しない。

### 4. ログをわかりやすくする

通常の `success` / `error` に加えて、必要に応じて以下を区別できるメッセージを残す。

- 全体ロック取得不可によるスキップ
- 同一 `fileId` が処理中または処理済みのためスキップ
- 既に `01input` 外へ移動済みのためスキップ

## テスト計画

### 1. clickpostReport

- 自分のGoogleアカウントで `clickpostReport` CSVを投入する。
- 出力CSVが `04output` に1件だけ作成されることを確認する。
- 元ファイルが `02processed` に移動することを確認する。
- 共有ユーザーのGoogleアカウントでも同じ確認を行う。
- 共有ユーザー投入時に出力CSVが無限生成されないことを確認する。

### 2. 同時実行

- `processInputFolder()` を短時間に複数回実行する。
- 同一 `fileId` が1回しか処理されないことを確認する。
- 同じファイル名で `success` と `error` が連続記録されないことを確認する。

### 3. 通常の子GAS振り分け

- `act_`、`ピッキング`、`rpp_`、`YYYYMMDD_item_list.csv` の対象ファイルで従来どおり処理されることを確認する。
- 処理成功時は `02processed`、失敗時は `03error` に移動することを確認する。

### 4. エラー時

- 意図的にエラーになるCSVを投入する。
- `03error` へ移動することを確認する。
- `processing` 状態が残らず、後続処理が止まらないことを確認する。

## 受け入れ条件

- 共有ユーザーが投入した `clickpostReport` CSVでも出力CSVが1件だけ作成される。
- 同一 `fileId` の二重処理が発生しない。
- 同じファイル名で `success` と `error` が連続記録されない。
- `log` の処理結果とDrive上の移動先が一致する。
- 既存の子GAS連携仕様を変更しない。

## 前提

- 共有ユーザーには対象フォルダへのファイル追加権限がある。
- 今回は親GASの再入防止を優先し、子GAS側の仕様変更は行わない。
- `DriveApp.addFile()` / `removeFile()` を使った既存の移動方式は維持する。
- 実装は別作業として行い、この計画書作成時点ではコード変更しない。
