# 親GAS二重実行防止計画

作成日: 2026-04-10

## 概要

`01input` に置いた同一ファイルに対して、親GAS `processInputFolder` が短時間に複数回動作し、以下のような症状が発生した。

- スプレッドシートには正常に取り込まれる
- その直後に同じファイルが再度処理される
- 子GAS側で重複日付エラーになる
- 親GASの `log` に同一ファイル名の `success` と `error` が混在する
- `02processed` と `03error` の配置結果が直感とずれる

今回の本質的な課題は、**親GAS側に同時実行・二重処理防止がないこと** と考える。

---

## 目的

親GASで同一ファイルが複数回処理されないようにし、以下を満たす。

- 同一タイミングで `processInputFolder` が重なっても二重実行しない
- 同じ `fileId` を複数回子GASへ送らない
- 成功済みファイルが後続実行で `error` 扱いにならない
- `log` と Drive 上の移動結果が一致する

---

## 原因仮説

### 1. `processInputFolder` の同時実行

- 1分トリガーの実行中に、次の実行が重なった可能性がある
- 並列実行された複数の親GASが同じ `input` フォルダの同じファイルを拾う

### 2. ファイル単位の処理済み管理がない

- 現状は `getFiles()` で取得したファイルをそのまま順番に処理している
- 既に他実行で処理中または処理済みかの判定がない

### 3. 移動前に別実行が子GASを呼ぶ

- 1回目の実行で成功しても、移動が終わる前に2回目の実行が同じ `fileId` を送る可能性がある
- 子GAS側では重複日付として `error` になりうる

---

## 実装方針

### 1. スクリプト全体ロックを導入する

`processInputFolder` の冒頭で `LockService.getScriptLock()` を取得する。

方針:

- ロック取得に成功した実行だけが処理継続
- 取得できない実行は即終了
- ロック待機時間は短めにし、長時間待たせない

想定:

- 二重起動の大半はこれで防止できる

### 2. `fileId` 単位の処理中・処理済みガードを入れる

`PropertiesService` を使い、`fileId` ごとに状態を持つ。

状態案:

- `processing`
- `done`

ルール:

- ファイル処理開始前に `processing` を記録
- 正常終了時に `done` を記録
- 既に `processing` または `done` の `fileId` はスキップ

補足:

- `done` は最低限の保持期間を設ける
- 永続的に残しすぎないよう、タイムスタンプ付きで古い記録は掃除できる形にする

### 3. フォルダ存在確認を入れる

処理前に、そのファイルがまだ `01input` に存在するかを確認する。

確認内容:

- 他実行で既に `02processed` または `03error` に移っていないか
- `input` フォルダから外れていたら処理しない

### 4. ログを「処理」と「スキップ」で分ける

今後は以下を区別してログへ出す。

- 実際に子GASへ送った処理
- ロック取得不可で全体スキップ
- `fileId` 重複で個別スキップ
- 既に `input` 外へ移動済みでスキップ

これにより、異常なのか意図した再入防止なのかがログで判断できるようにする。

### 5. 失敗時の状態解除ルールを決める

`processing` のまま固まるのを避けるため、失敗時の扱いを明確にする。

基本方針:

- 子GAS実行失敗時は `done` にしない
- ただし `processing` を残しっぱなしにしない
- finally で `processing` を解除する
- 本当に成功した場合のみ `done` に更新する

## 実装イメージ

### `processInputFolder`

- スクリプトロック取得
- `input` フォルダ走査
- 各ファイルごとに `fileId` をキーに処理可否を判定
- 可なら子GASへ送信
- 結果に応じて `processed` / `error` へ移動
- 状態更新とログ出力
- finally でロック解放

### 個別ファイル処理ガード

- `canProcessFile_(fileId)`
- `markFileProcessing_(fileId)`
- `markFileDone_(fileId)`
- `clearFileProcessing_(fileId)`
- `cleanupOldProcessMarks_()`

補助関数として切り出し、主処理を読みやすく保つ。

## テスト観点

### 1. 単一実行

- 通常の1回実行で従来どおり処理できる
- success 時は `02processed`
- error 時は `03error`

### 2. 同時実行

- `processInputFolder` を短時間に複数回実行しても、同一ファイルが1回しか子GASへ送られない
- 重複ログが大量発生しない

### 3. 同一ファイル再検知

- success 済みの `fileId` は後続実行でスキップされる
- `item_list.csv` が success 後に重複エラー化しない

### 4. 失敗時

- 子GASエラー時は `03error` に移動する
- 失敗後に `processing` 状態が残留しない

### 5. Drive結果整合

- `log` の `success/error` と Drive フォルダの実際の配置が一致する

---

## 受け入れ条件

- 同じファイル名で `success` と `error` が連続記録されない
- 同一 `fileId` の二重送信が起きない
- `02processed` と `03error` の結果がログと一致する
- 既存の子GAS連携仕様は変更しない

---

## 補足

- 今回の問題は子GASの取込そのものではなく、親GASの再入防止不足が主因と考える
- 子GAS側の重複日付エラーは防波堤として有効だが、親GASで二重送信しない構造に直す方が本筋
